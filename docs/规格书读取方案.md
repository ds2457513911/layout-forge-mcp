# 规格书读取方案（datasheet reading scheme）

> 建档：2026-10-13 ｜ 样本：`Data\footprint_test\NB_LYDPJ_5P_12X6\LYDPJ-H23CB1Y-053N.pdf`
> 结论口径：**先判文件形态，再选读法**。同一个"读尺寸数字"目标，矢量 CAD 图、印刷规格书、扫描件要走三条不同的路。

---

## 1. 为什么要先判形态

建封装的真实成本在"读规格书提参数"。读法选错的代价不对称：

- 对**矢量 CAD 图**去做 OCR/文档解析 → 白花力气（图里根本没有排版文字）。
- 对**扫描件**去提文本层 → 直接失败（文本层 0 字符）。
- 对**印刷规格书**去逐页读整页图 → 贵（每页一张图，且低分辨率会读错数字）。

判定只需三个数：`页数 / 位图数 / 文本字符数`。判据：

| 形态 | 特征 | 主读法 |
|---|---|---|
| **矢量 CAD 图**（AutoCAD/Altium 出图） | 位图 0 张、矢量图元成百上千、文本字符数接近 0（尺寸是 SHX 字形轮廓） | 坐标裁剪 + 高 dpi 重渲染；矢量量距做交叉校验 |
| **印刷规格书**（半导体厂 PDF） | 文本层厚（数千字符）、有图有表 | 文本层提参数（表）+ 局部高 dpi 读图（land pattern） |
| **扫描件** | 文本 0 字符、位图覆盖整页 | 缩略图拼版定位 → 高 dpi 裁剪 → 视觉读数（必要时 OCR 兜底） |

判形态用 `services/pdf_service.py::_count_text_chars` + `page.get_images()`/`get_image_info()` 即可，零成本。

## 2. 样本实测（LYDPJ-H23CB1Y-053N.pdf）

```
metadata : creator = AutoCAD 2014 - 简体中文, producer = pdfplot11.hdi 11.1.108.0
pages    : 1        （A4 横版 842 x 595 pt，page.rotation = 270）
位图     : 0 张（get_images 空、get_image_info 空）
矢量图元 : 3216 条（get_drawings）
文本字符 : 43 个 —— 全部是三个签名（michael / JIM / Andy 2015.8.9，
           CommercialScriptBT-Regular），**没有任何一个尺寸数字是文字对象**
图元范围 : 显示坐标 (2.8, 4.3) – (840.0, 591.1)
```

**结论：这不是扫描件，是 AutoCAD 矢量出图。** 尺寸数字被 plot 成了 SHX 字形轮廓（线条几何），所以拿不到文本层。

对方案的两个影响：

1. **坏消息**：任何"提 PDF 文本层拿数字"的路子在本件上 100% 无效 —— 尺寸字符数为 0。
2. **好消息**：比扫描件好处理得多。矢量→位图渲染没有模糊、没有倾斜、没有噪点与 JPEG 伪影；可以**按任意 dpi 重渲染任意区域**，不存在"放大糊掉"的上限。这一点是真扫描件做不到的。

## 3. 四档读法（按成本递增，默认只用档 1）

### 档 1（默认）：坐标裁剪 + 高 dpi 重渲染

不用"整页缩小定位"——本件只有 1 页，没有页要定位。直接在 PDF 坐标里裁 land pattern 区域，按 600–1200 dpi 重渲染。

```python
# page 用显示坐标（已含 rotation）；clip 与 page.rect 同一坐标系
pm = page.get_pixmap(dpi=900, clip=pymupdf.Rect(598, 55, 728, 130))
```

与"整页缩小拼版"的本质区别：**缩的是视野，不是像素密度**。
拼版把 11 页塞进一张图，单页像素密度被稀释到 72 dpi；裁剪放大保住 600–1200 dpi。两者不冲突，前者管"找哪一页/哪个视图"，后者管"读准数字"。

实测（本样本，600 dpi）：

| 区域（显示坐标 pt） | 内容 | 输出 |
|---|---|---|
| `(590, 20, 762, 250)` | PCB LAYOUT TOP VIEW 整视图 | 1434×1918 |
| `(598, 55, 728, 130)` | 焊盘行 + 12.20/11.40/6.45/3.65 标注 | 1084×626 |
| `(545, 400, 745, 560)` | PLUG SPEC | — |

600 dpi 下 `1.50 / 2.10 / 5.90 / 6.45` 这类小数字笔画边缘锐利、完全可读。
**参数口径**：常规尺寸 600 dpi 起；亚毫米标注或公差带用 900–1200 dpi。

### 档 2：矢量量距（交叉校验，别当主读数）

全图统一比例，几何可以直接换算 mm。本样本实测：

- 视图本体宽 116.16 pt ↔ 标注 12.20 mm → **≈9.52 pt/mm**（与标题栏 SCALE 1:1 **不符**，实际约 1:3.3 —— 标题栏不可信，必须实测标定）
- 比值交叉验证：几何量出的 ①→② : ②→⑤ = 1.770，标注 2.80 : 4.95 = 1.768 → 吻合到 0.1%
- 说明图纸**是等比绘制的**，量距在原理上成立。

用法：把区域内的图元做连通域聚类 → 取每个焊盘的外接框与中心 → 直接输出 pad 尺寸与 pitch（mm），**零 OCR 误差**。

**但有两个前提，不满足就不能用**：

1. **必须一次性标定 pt/mm**：标题栏的比例标注不可信；要么用一条已知标注的两条界线精确坐标反推，要么用图纸标准边框。
2. **焊盘与器件本体轮廓在几何上是粘连的**：本样本用 gap=0.6pt 做连通域，5 个焊盘全被并进本体轮廓成为一个 160×141 pt 的大块。要切开得靠填充色 / 图层 / 子路径归属来区分 —— 是工程量，不是一行代码。

定位：**做标注读数的交叉校验**（和档 1 的读图结果对拍），暂不做主读数手段。

### 档 3：OCR 兜底（只对付成段文字）

NOTES 段（接触电阻 50 mΩ、额定电流 1A、耐久 5000 次……）和件号表这类成段文字，可以整块 OCR 一次取出，比让 AI 逐行读图便宜。

- 本项目 `.venv` 目前**没有 OCR 引擎**（无 tesseract / paddleocr）。要启用需另行安装，属可选增强。
- **不建议对尺寸数字走 OCR**：`1.50 / 5.90` 这类小字号数字，OCR 的错读率高于直接视觉读数，而错读一个数字就是整批封装报废。

### 档 4：明确不要做的

- **不要为这类文件上"datasheet 专用模型"**（PaddleOCR-VL / dots.ocr / MinerU 等文档解析模型）。它们是给**排版文档**（文字+表格+公式）做结构化的；本件是 CAD 图，没有排版文字，模型无用武之地。
- **不要把客户规格书上传到 SheetsData 这类云端 MCP**（数据上云）。
- **不要用低 dpi 整页图读数字**。已有实测教训：200 dpi 整页把 `0.5` 读成 `0.7`，450 dpi 区域裁剪才读对。

## 4. 落地到项目（建议）

给 `services/pdf_service.py` 加三个能力，MCP 侧暴露成工具：

| 新工具 | 输入 | 输出 | 用途 |
|---|---|---|---|
| `render_pdf_region` | `pdf_path, page, rect(x0,y0,x1,y1), dpi` | 图片路径 | 档 1 主读数 |
| `pdf_probe` | `pdf_path` | 页数/位图数/文本字符数/形态判定 | 开跑前判形态，零成本 |
| `measure_region` | `pdf_path, page, rect` | 连通域外接框 + 中心距（pt 与 mm） | 档 2 交叉校验 |

推荐流程：

```
pdf_probe                      → 判形态（CAD 图 / 印刷 / 扫描件）
  ├─ CAD 图   ：render_pdf_region(rect, 900) → 读数 →（可选）measure_region 对拍
  ├─ 印刷规格书：文本层提表 + render_pdf_region(land pattern, 600) → 读数
  └─ 扫描件   ：contact_sheet 定位 → render_pdf_page/region 裁剪 → 读数
```

`pdf_probe` 与现有 `_count_text_chars` 是同一套判断，只是提前到流程第一步，避免"选错读法"这种不可逆的浪费。

## 7. 与现有 SKILL / 外部工具的关系（2026-10-13 补，回答"能不能提速"与"为什么不用现成工具"）

### 7.1 现状工具能力（`mcp_server/tools.py` 实查）

| 工具 | 能力 | 硬上限 |
|---|---|---|
| `locate_land_pattern_page` | 文本关键词打分定位页 | 文本层稀薄件失配（实测 13 份中 5 份 `no_match`） |
| `render_pdf_page` | 整页渲染 | **固定 150 dpi**（`pdf_renderer.DEFAULT_PYMUPDF_DPI`），**无 clip / 无 dpi 参数**，带缓存 |
| MCP resource `datasheet://{stem}/page/{n}` | 同上 | 同上（走同一个 `get_or_render_image`） |
| `render_pdf_contact_sheet` | 缩略图拼版定位 | 72 dpi、单页宽 210 px，**只够定位，不能读数** |

### 7.2 关键发现：现有 SKILL 自相矛盾

`allegro-footprint-check` 的「分辨率铁律」要求「裁到区域 + 提高 dpi（≥400）」；
同一文件的禁止条 5 又要求「PDF 图纸必须通过 resource 或 `render_pdf_page` 读图」。
而这两条通道**上限都是 150 dpi 整页，物理上做不到 ≥400 dpi 区域裁剪**。
即：这条铁律目前只能靠 AI 手写 PyMuPDF 满足，而手写又与"必须走工具"的规定相抵。

### 7.3 本方案的增量（按重要性）

1. **补工具缺口（最大块）**：把「区域 + 高 dpi」从"要 AI 手写脚本"变成一次工具调用
   （`render_pdf_region`），让 SKILL 自己写的铁律变成可执行。**不是新读法，是让已有规则能落地。**
2. **判形态前置（`pdf_probe`）**：一次零成本调用判出 CAD 矢量 / 印刷 / 扫描件，
   避免"选错读法"这种不可逆浪费（对 CAD 图做文本提取、对扫描件提文本层都是纯白工）。
3. **矢量量距交叉校验（`measure_region`）**：全新能力，量出的 pad/pitch 与读图结果对拍。

### 7.4 效率对比（"读一份新规格书"口径）

| 文件形态 | 现在 | 本方案 | 变化 |
|---|---|---|---|
| 印刷规格书（文本层厚） | locate 命中 → 读 1 张 150dpi 整页 | probe → 文本层提表（0 张图）或 region 裁剪 600dpi（1 张小图） | 张数持平或更少；**消除 150dpi 误读** |
| 扫描件（11 页） | locate 失配 → 拼版 1 张 → 读 1 张 150dpi 整页 | probe → 拼版 1 张 → region 裁剪 900dpi | 张数相同；**第二张更小、更清晰** |
| CAD 矢量件（1 页，本 LYDPJ） | locate 失配 → 拼版 1 张（对 1 页无意义）→ 读 150dpi 整页（大概率误读） | probe 判 CAD → **跳过定位** → region 裁剪 900dpi | **2 张 → 1 张**，分辨率 6× |

**诚实口径**：省下的第一张图有限（首次读新件仍可能要看一张整页图才取得 rect 坐标）；
真正的大头是**避免误读返工**——SKILL 已有 `0.5` 读成 `0.7` 的实锤，错一个数字就是整批封装报废。

### 7.5 为什么不用上一轮调研的外部 SKILL / MCP / 读图模型

根因一句话：**它们解决"印刷体文字与表格"，本案的难点是"机械图上的标注数字"。**

| 候选 | 为什么不合本例 |
|---|---|
| `ee-datasheet-master` / `datasheet-p2p-compare` / `hw-datasheet-compare` | 读的是半导体数据手册的**文本表**（pinout / 电气 / 时序）。本件是 AutoCAD 出图，**文本层只有 43 个签名字符**，尺寸是 SHX 字形轮廓 → 无可提取文本 |
| `paddleocr-doc-parsing` / `mineru-*` / `paddleocr-vl-locally` | 给**排版文档**做结构化（文字+表格+公式）。CAD 图没有排版文字；本案要的是尺寸数字，OCR 对小字号数字错读率高于视觉直读 |
| SheetsData MCP（`read_datasheet` / `analyze_image`） | ① 公开 beta 且**数据上传云端**，客户规格书不能外传；② 同上是文档语义读取，不解决标注精读 |
| `pdf-mcp`（I-CAN-hack） | 唯一可借鉴的是 **TOC 书签跳页**（比关键词打分稳）。但书签只在**文本层厚的印刷件**上有；CAD 图与扫描件都没有书签。且这能力用一行 PyMuPDF 即可实现，不必引入整个 MCP |
| PaddleOCR-VL 0.9B / dots.ocr / MinerU2.5 / DeepSeek-OCR | 通用文档解析 VLM，强项是"图→结构化文本"，**不解决数字精度**；本地部署还要 CUDA+权重+推理链，运维成本远超收益。唯一有边际的场景是扫描件里的大段 NOTES 文字 → 归入档 3 OCR 兜底即可 |

治理层面另两条：
- `allegro-footprint-check` 禁止条 5 的意图是「不让 AI 手写 PyMuPDF 解析 PDF 结构」；
  引入一个自动解析 PDF 的外部 skill，与该规则的精神相冲突，需先厘清边界。
- 装第三方 skill 须先过安全审计；而上述候选覆盖不了本案难点，边际收益低。

## 8. 动工风险清单（2026-10-13 逐项实测，回答"动工是否只有优化、不会出现副作用"）

### 8.1 结论先说

**不能无条件保证零副作用。** 有 5 项真实风险（R1–R5），其中任何一项被"随手写"破坏都会产生实际损害；
另有 **2 项动工前就已存在的隐患**（P1/P2），与方案本身无关，但会被动工放大。
**把这 7 项全部约束住之后，动工是纯新增 —— 既有 31 个工具行为不变，可做到零副作用。**

### 8.3 必须约束的 5 项真实风险

| # | 风险 | 触发条件 | 必须的约束 | 验证方法 |
|---|---|---|---|---|

| **R4** | 形态分类是启发式，**阈值可能误判** | 实测 17 份：`printed` 12 / `cad_vector` 3 / `scan` 1（另 1 份重复）。如 FPC 0.5-30P 仅 128 字符被判 `cad_vector`；TF 卡座 325 字符被判 `printed`（实际文本层很薄） | 分类结果**只能建议读法、不能当事实**；三条路对任何 PDF 都可用（区域裁剪是通用兜底），**误判只影响选路、不影响结果** | 逐份人工抽查分类合理性 |
