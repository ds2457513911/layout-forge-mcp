# 通道并发-实现事实核对

本文核对四件事：`Workspace.open(workspace_id=...)` 到底建立了什么；SkillBridge 的回复在多客户端之间怎么路由；fastmcp 4.0.10 在同一 stdio 进程内是否并发执行多个 `tools/call`；以及这台机器上是否有现成的跨进程文件锁条件。目的只是把代码事实钉死，供一张决策票引用，不讨论方案取舍。

结论一句话：**回复通道只有一条、帧里没有请求 ID，而服务端同时只受理一个客户端连接——所以跨进程的双任务不会互相读到对方回复，后到者会在 `open` 握手阶段抛「通道无法对齐」；真正结构可达的「A 读到 B 的回复」路径在同一 MCP 进程内部：两个 `tools/call` 真并发，共享同一个无锁 `Channel`。**

## 一、`Workspace.open(workspace_id=...)` 做了什么

**结论**

1. 进程内一张模块级缓存表：同一 `workspace_id` 第二次 `open` 直接返回同一个 `Workspace` 对象（同一个 socket），不新建连接。
2. 跨进程没有任何共享：每个进程各自 `connect()` 一条独立 TCP 连接，彼此不知道对方存在。
3. 库层面**没有**任何互斥、排队、文件锁。唯一的仲裁在服务端，而且是「拒绝」，不是「排队」。

**证据**

- `.venv/Lib/site-packages/skillbridge/client/workspace.py:21`：`_open_workspaces: dict[WorkspaceId, Workspace] = {}` —— 模块级、进程内、进程退出即消失。
- `workspace.py:279-287`：`if workspace_id not in _open_workspaces:` → `channel_class = create_channel_class(force_tcp)` → `channel = channel_class(workspace_id)` → `_open_workspaces[workspace_id] = Workspace(channel, workspace_id)`；命中缓存时直接 `:287 return _open_workspaces[workspace_id]`。**没有锁，没有 `open` 状态检查。**
- `workspace.py:289-296`：`close()` 关 channel 并 `_open_workspaces.pop(self.id, None)` —— 任一调用方关闭，就把别的调用方正用的连接从缓存里摘掉。
- `.venv/Lib/site-packages/skillbridge/client/channel.py:100-105`：`connect()` = `settimeout(1)` → `connect()` → `settimeout(None)`（之后 `recv` 是无限等待）。
- `channel.py:187-214`：`create_channel_class` 在 Windows（或 `force_tcp`）下用 TCP，地址为 `('localhost', int(id_))`（`:214`），`id_` 必须是 0–65535 的数字（`:209`）。本项目 `workspace_id` 就是端口 `7777`（`mcp_server/config.py` 的 `SKILLBRIDGE_WORKSPACE_ID = "7777"`）。
- 服务端的「一次只一个」：`.venv/Lib/site-packages/skillbridge/server/python_server.py:49-81` 的 `SingleTcpServer` 带实例标志 `active`，`:71-77` `verify_request` 在 `active` 为真时直接 `return False`；`:84-85` `ThreadingTcpServer(ThreadingMixIn, SingleTcpServer)` 继承同一实现。`:50 request_queue_size: int = 0` → `listen(0)`，连等待队列都没有。

**查不出**：库有没有「id 被占用」这类检测逻辑——没有，全文件只有上面那张 dict；已在 `workspace.py`（372 行）全文、`channel.py`（228 行）全文搜索 `Lock`、`mutex`、`flock`、`queue`，零命中。

## 二、回复怎么路由（本票最关键）

**结论**

1. Allegro 侧与 Python 服务之间**只有一对 stdin/stdout 管道**，Allegro 对输入**每一行**回一帧，帧内容只有 `success <值>` / `failure <错误>`，**没有任何请求 ID 或序号**。
2. Python 服务端所有客户端共用这同一对管道：处理请求时先往 stdout 写一行，然后阻塞在 `stdin.readline()` 等**下一行**——回复按到达顺序先进先出，谁先 `readline` 谁拿走，与它处理的是哪个客户端的请求无关。
3. 但服务端只受理**一个**客户端连接（`verify_request`），所以第二个进程根本发不进来；「进程 A 发一条、进程 B 发一条、A 读到 B 的回复」在装配好的服务上**不可达**，可达的是「B 连接被拒 → B 在握手阶段失败」。

**证据**

- `.venv/Lib/site-packages/skillbridge/server/python_server.il:198` `defun(pyStartServer (@key (id "default") (logLevel "INFO") (singleMode nil) (timeout nil) (python "python") (forceTcp nil) ...))`；`:215` 只调用一次 `ipcBeginProcess(executableWithArgs "" '__pyOnData '__pyOnError '__pyOnFinish ...)`，句柄保存在 `pyStartServer.ipc` —— 一个进程只有一个回调、一对管道。
- `python_server.il:71-92` `__pyOnData(id data)`：`:73 foreach(line parseString(data "\n") ...)` 逐行求值，每行写回**同一个 id**：`:78 ipcWriteProcess(id lsprintf("failure %L\n" ...))`、`:85 ipcWriteProcess(id lsprintf("success %s\n" ...))`、`:87 ipcWriteProcess(id "success error('unbound')\n")`。帧里没有 ID 字段。
- `python_server.il:11-21` `pyKillServer` 只是 `ipcWriteProcess` 杀子进程并把 `pyStartServer.ipc` 置 nil —— 管道随即消失，这就是「重启能清空队列」的全部机制。
- `python_server.py:133-159` `handle_one_request`：`:134` 读 10 字节长度 → 读正文 → `:150 send_to_skill(command.decode())`（`:32-35` 写 stdout 并 flush）→ `:152 result = read_from_skill(data_ready).encode()`（`:38-46` 就是 `stdin.readline()`，Windows 分支 `win_data_ready()` 恒 `True`，无超时）→ `:155-156` 把结果写回该客户端 socket。
- `python_server.py:71-77` 的 `verify_request`：`if self.active: return False`，否则 `self.active = True`；`:79-81` 在连接结束（`finish_request`）时清回 `False`。`:88-89 create_tcp_server_class` 只在 `SingleTcpServer` 与 `ThreadingTcpServer` 之间选，两个都有这个守卫；`pyStartServer` 默认 `singleMode nil`（`python_server.il:198`），项目 `restart_server` 也不传 `--single`（`services/skillbridge_writer.py:378-420` 的 `prog1(... pyStartServer ?id ... ?python ... ?forceTcp t)`）。
- 跨进程失败怎么表现：`channel.py:142-157` `_receive_only` 的 `:144 self.socket.recv(10)` 收到空字节 → `:149-150` 抛 `RuntimeError("The server unexpectedly died")`；若 `sendall` 先失败，则走 `:117-140` 的 `reconnect()` 重连重发，仍然落到同一处。`services/skillbridge_writer.py:299-309` `_send_raw` 把**所有**异常包成 `SkillCallError`；`:283-285` `_handshake` 只 `except SkillCallError: continue`，最多 `:276 limit = lag + 8` = 24 轮，然后 `:287-297` 抛 `ConnectionError`「通道无法对齐……」并提示 `pyKillServer()`。
- 同进程共享连接：`workspace.py:279-287` 返回缓存对象，`channel.py:159-161` 的 `send` 是 `self._send_only(data)` 再 `return self._receive_only()` 两个独立动作，二者之间**没有锁**。两个线程各自走到 `recv(10)` 时，先调度的线程拿到队列里**第一条**回复帧——它未必是自己那条请求的。

**关于「固定深度约 15 帧」**：`15` 在代码里**查不出**——`python_server.il`、`python_server.py`、`channel.py` 全文没有这个数字，`skillbridge_writer.py:228-256` 只有实测注释（`sent=ZZ037 -> recv=ZZ022`，另记 `recv[20] == '__P005__'`），`_handshake` 的默认参数取整为 `lag = 16`（`:235`）。管道缓冲深度由操作系统决定，源码无对应常量；本次未做运行时测量。可确证的只是**机制**：每行输入必回一帧（`python_server.il:73`），而一次 `send` 只读一帧（`python_server.py:152`），任何没被读走的帧都会永久滞留在管道里，且「发一收一」使积压长度守恒（`channel.py:159-161` 的成败不可分离）。另：`.venv` 里的 `python_server.py` 与 `dist-info/RECORD` 记录的哈希不符（记录 6978 字节，实际 7156 字节），与 uv 缓存里的上游 1.8.0 版本 diff 后**只有 Unix 分支的类改名**（`SingleUnixServer`→`TCPServer`），Windows 分支的 `verify_request`、`handle_one_request`、`read_from_skill` 一字未改。

## 三、fastmcp 4.0.10 在 stdio 模式下是并发还是串行

**结论**：**并发**。同一 MCP server 进程内两个 `tools/call` 可以同时在两个 anyio 工作线程里跑，互不排队（上限是线程池容量，默认 40）。

**证据**

- `mcp_server/server.py:28 mcp = FastMCP("layout-forge-mcp")`，`:57` `mcp.run()`（fastmcp 默认 stdio）。
- 工具写法是**同步函数**：`mcp_server/tools.py:140-141 @mcp.tool()` + `def list_subfolders(...)`，全文件 20 余个工具同为 `def`（`mcp_server/tools.py:159-160`、`:180-181`、`:219-220` 等）。
- 派发链：`fastmcp/server/mixins/mcp_operations.py:125` 注册 `tools/call`；`:222` `async def _on_call_tool`，`:255 result = await self.call_tool(key, arguments, version=version)`；`fastmcp/server/server.py:1376 async def call_tool`；`fastmcp/tools/function_tool.py:369-404 run()` → `:405-451 _run_body()` → `:452 _execute()`。
- 同步工具进线程池：`function_tool.py:477-481` `elif self.run_in_thread:` → `result = await call_sync_fn_in_threadpool(type_adapter.validate_python, arguments, strict=strict)`；`run_in_thread` 默认 `True`（`:172`、`:528`）。`fastmcp/server/dependencies.py:756-757`：工具没有 `Context`/`Depends` 参数时 `without_injected_parameters` **直接返回原函数**，所以线程池里跑的就是工具函数体本身（不是只做参数校验）。
- `fastmcp/utilities/async_utils.py:9` 导入 `anyio.to_thread.run_sync`，`:26-34 call_sync_fn_in_threadpool` 直接 `await run_sync_in_threadpool(...)`；anyio 默认线程上限 40（`.venv/Lib/site-packages/anyio/_backends/_asyncio.py:3162 limiter = CapacityLimiter(40)`）。
- 协议层不串行化：`mcp/server/runner.py:496` 与 `:733` 都只把 `initialize` 设为内联（`inline_methods=frozenset({"initialize"})`）；`mcp/shared/jsonrpc_dispatcher.py:592-606`：只有 `inline_methods` 在读循环里等待，其余请求走 `:606 self._spawn(self._handle_request, req, dctx, scope, on_request, sender_ctx=sender_ctx)` 派发成并发任务。
- 落到本项目：工具内部用 `with AllegroSession(workspace_id) as s:` 取会话（`services/footprint_builder.py:784`、`:1032`、`:2216` 等二十余处），而 `Workspace.open` 命中进程缓存（`workspace.py:279-287`）→ 两个并发调用拿到的是**同一个 `Channel`**，见第二节最后一条。

## 四、跨进程锁的现成条件

**4.1 `msvcrt.locking` 在本机 Windows 的实测行为**（Python 3.12.10，`C:/Users/ds245/.dsh/office/runtime/venv/Scripts/python.exe`；探针脚本写在系统临时目录、跑完即删，未落进仓库）

| 问题 | 实测结果 |
| --- | --- |
| 能否独占 | 能。A 持锁时，另一进程 `LK_NBLCK` 立即失败：`PermissionError` / `EACCES`（errno 13） |
| 进程崩溃后是否自动释放 | 是。`taskkill /F` 杀掉持锁进程后 1 秒内，其它进程立刻能拿到锁，不需要任何清理代码 |
| 是否可重入 | **否**。同一进程用第二个文件句柄再锁同一字节，同样 `EACCES` |
| 会不会改文件内容 | 不会（锁前锁后 4 字节文件内容一致） |
| 前提 | 文件句柄必须保持打开；`locking` 从当前文件位置起锁 N 字节 |

**4.2 仓库与依赖现状**

- `services/`、`mcp_server/`、`Tools/` 下**没有任何跨进程文件锁**：全量搜索 `msvcrt`、`filelock`、`portalocker`、`LockFileEx`、`CreateMutex`、`fcntl`、`.lock`（排除 `.venv`、`.git`）零命中。
- 当时唯一的锁是**进程内**的（`convention_engine` 的 `threading.Lock()`，该模块已随票 #22 删除）；票 #10 定案后新增 `services/channel_guard.py`：进程内 `RLock` + 跨进程 `msvcrt.locking` 文件锁，`AllegroSession` 已内置。
- `pyproject.toml` 的运行依赖只有 `fastmcp`、`skillbridge`、`PyMuPDF`、`pdfplumber`；`uv.lock` 中 `filelock`、`portalocker` 各 0 条；`.venv/Lib/site-packages` 下也没有这两个包。
- 与 Allegro 自己的 `*.dra.lck` 不是一回事：那是 Allegro 的 drawing 锁文件，仓库里没有读写它的代码。
- 相关入口只做安装/重启、不碰锁：`Tools/install_skillbridge.py:81` 在 `.venv` 里 glob `skillbridge/server/python_server.il`、`:320` 往 `allegro.ilinit` 写 `load("{il}")`；`Tools/restart_skillbridge.py` 只调 `AllegroSession.restart_server`（`services/skillbridge_writer.py:378-503`）。

## 五、对本票的含义

1. 「两个建图任务同时跑 → 回复队列错位、只能重启清」这条断言，在**跨进程**场景下与代码不符：第二个进程的连接会被 `verify_request` 挡掉，症状是 `open` 阶段抛「通道无法对齐」，而不是静默串话；要复现「读到别人的回复」，必须先解除单客户端守卫。
2. 真正在现装配下可达的串话路径只有一条：同一个 MCP 进程内两个 `tools/call` 并发（fastmcp 同步工具进线程池，上限 40），经 `Workspace.open` 缓存共享同一个无锁 `TcpChannel`，两个线程的 `send`/`recv` 可以交叉配对。
3. 单管道 + 无请求 ID 是「错位」能够发生的结构前提：Allegro 每行必回一帧（`python_server.il:73-87`），客户端一次只读一帧（`python_server.py:152`），未被读走的帧永久滞留，且「发一收一」让积压守恒——这部分与文档描述一致。
4. 「约 15 帧」只存在于实测注释（`services/skillbridge_writer.py:228-256`），代码里没有该常数，`_handshake` 用的是 `lag = 16`；管道缓冲深度由操作系统决定，本次未测出定量来源。
5. `msvcrt.locking` 满足「独占 + 进程崩溃自动释放」两个条件，但**不可重入**（同进程第二个句柄同样 `EACCES`）；仓库当前没有任何跨进程锁、也没有 `filelock`/`portalocker` 依赖，要用只能走标准库或新增依赖。

## 六、落地结果（票 #10 执行后补记，2026-11-19）

上文的事实核对没有一条被实现推翻，只是把结论落成了代码：

1. **通道级锁** `services/channel_guard.py`：进程内 `threading.RLock`（可重入，depth 0→1 才碰文件）+ 跨进程 `msvcrt.locking(LK_NBLCK)` 锁 `Tools/log/skillbridge.lock`（1→0 才放）。同进程第二线程**按超时报**而不是排队 —— 因为 fastmcp 的线程池让同进程并发是真会发生的（上文 §五.2）。
2. **持有人文件** `Tools/log/skillbridge.lock.holder`（pid / tid / 起始时间 / 任务名 / drawing），撞锁时读出来填进 `CHANNEL_BUSY` 的 `holder` 字段；文件用「临时文件 + `os.replace`」原子写。
3. **崩溃自愈**：`msvcrt` 的文件锁随进程终止由内核释放（上文 §五.5 实测），所以 `taskkill /F` 之后**不需要**人去删锁文件；实测重取耗时 0.00–0.36 s。
4. **建图租约** `TaskLease`（`Tools/log/build_footprint.lease`，`O_CREAT|O_EXCL`）：撞上**只报告不排队**，返回持有人；重入判据是「同 pid **且**同 tid」，尸体租约（pid 已死）自动接管。
5. **错误分工**：`CHANNEL_BUSY` = 通道被占（等/重试，**不要** `pyKillServer()`）；`CHANNEL_NOT_READY` = 通道本身不可用（服务没起/队列积压，要人处理）。`_handshake` 一个回复帧都没收到时先看锁：别人持有 → BUSY；否则 NOT_READY 且指引只写 `pyStartServer`。
6. **回归**：`eval/suites/behavior` 新增 B6（18 项断言），套件从 5 夹具变 6 夹具；`eval/check_eval.py` 五套全绿（60 s），`Tools/selfcheck_geometry.py` 239/239、`Tools/selfcheck_skill_syntax.py` 222/222。
